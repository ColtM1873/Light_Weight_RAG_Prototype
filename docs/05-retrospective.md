# 05 · 复盘

## 1. 最难的问题

### 1.1 文档冲突：怎么做到“不擅自选边”

D001 写 30 天，D002 写 15 天，D001 还有“十个工作日内整理票据”的流程性表述。难点不在检索，而在**模型很容易挑一个看起来更权威/更新的答案**。

最终做法：

- system prompt 明确：没有文档说明自己可以覆盖另一份时，必须列出冲突双方并请用户确认；
- Guard 2 把“文档冲突未列明”视为 `overclaim`；
- 让模型调用 `get_version_date` 核对版本日期，并在 finalize 里保留“待确认”状态；
- 案例 02/04 验证：模型列出 10 个工作日 / 15 天 / 30 天三种口径，没有擅自选一个。

### 1.2 引用校验：不暴露内部 `piece_id`

最初想把 `piece_id`/`piece_type` 也作为引用字段，但这会把检索实现细节泄露给用户，也增加模型填错的机会。最终只校验 `document_id + quoted_content`：

- `document_id` 必须在库中；
- 原文片段必须能在该文档任意单句/段落中找到（去标点后包含，或相似度 ≥ 0.75）。

这既足够拦截“编造引用”，又不强迫模型理解内部索引。

### 1.3 Guard 循环与“必须 finalize”

两个 Guard 都可能触发反馈，形成多轮循环。必须同时解决：

- 反馈不能把正确的 Model A 压服（话术是讨论，不是命令）；
- 解析失败要有上限，避免死循环；
- 最终一定给用户一版整理稿。

2026-11-14 的关键调整：**即使两个 Guard 一次通过，也必须 finalize**。此前“一次过直接 END”看起来省一次调用，但用户看到的可能是草稿，且无法保证“最终整理”统一发生。代价是每轮多一次 Model A 调用，换来一致的用户体验。

### 1.4 可观察性：Guard 在跑，但用户看不见

这是本轮最痛的教训。Guard 通过时没有消息，旧前端只显示 Human/Tool/AI，用户自然会问“Guard 真的在跑吗？任务状态呢？”

修复分三层：

1. 服务端把 Guard 1/2 的 `parsed_answer` / `support_verdict` 转成紫色卡片；
2. 每轮结束发蓝色“任务状态”卡（完成/冲突/资料不足 + 引用 + 缺口 + 步数）；
3. `Chat-History` 把完整结构化结果写入 JSON/Markdown，而不是只写“通过”。

### 1.5 中文路径 + FAISS

`faiss.write_index` 的 C++ `fopen` 不支持中文路径。改为 `serialize_index` + Python 写文件；solid 数据里的文档路径改为相对仓库根，仓库搬家/提交后仍可用。

### 1.6 工具失败要可复现

真实网络故障不可控。加 `RAG_FAULT_TOOL` / `RAG_FAULT_TIMES` 故障注入，让指定工具前 N 次调用返回失败信息。这样可以在不破坏真实工具的前提下，稳定演示“失败 → 换查询 → 成功”。

### 1.7 状态语义还不够细

案例 08 的 T3 是一个“附条件结论”：模型说“不能认定违规，但要区分设备/网络/是否真下班”。Model B 返回 `done=False` 且 `no_support=False`，最终显示“未完成 / 状态未知”。这说明当前 `done/conflict/no_support` 三态不够表达“有条件完成”。下一步应加 `conditional` / `needs_confirmation`，或让 Model B 对“已给出可执行结论”置 `done=True`。

## 2. 学习收获

- **确定性 vs 模糊判断**：引用匹配、ID 存在性必须用代码；LLM 只做抽取和支持性判断。把两者混在一起，调试成本会指数上升。
- **Guard 是产品能力，不是后台开关**：没有可见的状态和引用，用户无法信任 Guard；可观察性要一开始就设计。
- **反馈的质量决定循环能否收敛**：指出原文和缺口，比“你错了，重写”有效得多；同时要有重试上限和步数上限。
- **数据路径是长期成本**：早期“代码在 v1、数据在上一级”的约定，在提交/换机器时立刻变成负担；相对路径 + 单一 `paths.py` 值得。
- **AI 辅助的边界**：AI 可以快速搬代码、补测试、写文档，但产品规则（如“必须 finalize”“冲突不选边”）必须由人拍板并写进测试。

## 3. 下一步

1. **检索改进**：加 reranker（bge-reranker）或 BM25 混合检索；对“差旅/报销/住宿”这类高频词做同义词扩展。
2. **状态枚举扩展**：`done` / `conflict` / `no_support` / `conditional` / `needs_confirmation`，并让 Model B 明确区分“有结论但附条件”和“没有结论”。
3. **独立 Model C**：用更强模型或规则校验器降低“同源偏宽松”的风险；对引用做更严格的逐句蕴含判断。
4. **finalize 后复查**：至少做一次引用校验（不必再跑 Model C），防止整理稿改写引用。
5. **持久化**：`SqliteSaver` 替代 `InMemorySaver`，让 LangGraph 历史跨重启保留；`Chat-History` 继续作为原始审计记录。
6. **评测集**：把 8 个案例扩成 30+ 条带标注的评测集（问题、期望引用、期望状态），做回归。
7. **可观测性**：给 Guard 通过/失败、工具失败、步数上限加指标和日志；前端加“执行轨迹”折叠面板。
8. **前端**：支持 Markdown、引用高亮、工具结果折叠；当前是纯文本 + 截断，够用但不精致。
